# Android implementation plan

This is the Phase 1 audit plus the resulting design for moving from architecture scaffolding into real Android code. It builds directly on `android-readiness.md`, `android-api-contract.md`, `android-realtime-contract.md`, `android-webrtc.md`, and `android-games.md` from the prior architecture pass — this document doesn't repeat their findings, only the parts that changed or needed a concrete decision to start coding.

## Audit findings that changed since the last pass

Re-inspecting `server/src/routes/auth.js` while designing the auth flow surfaced one real gap the earlier audit missed: `issueSession()` only ever set an **HttpOnly cookie** — the JWT was never present anywhere in the JSON response body. `requireAuth` accepting a `Bearer` header (documented previously) is necessary but was not sufficient, because Android had no way to *obtain* a token to send as that header in the first place. This is fixed — see section D.

Everything else audited (REST contract, Socket.IO events, WebRTC boundary, game authority, moderation/security, environment/secrets, navigation structure on the web side, and the data models Android will consume) matched the prior pass's documents; nothing else required a change.

## A. Android architecture

Kotlin + Jetpack Compose, MVVM (`ViewModel` + `StateFlow` for UI state, `SharedFlow` for one-shot navigation/side-effect events — see `core:navigation`'s `NavigationEvent`), repository pattern (one repository per feature's data needs, e.g. `AuthRepository`), no separate UseCase layer yet — each repository method is already a single, named operation (`login`, `register`, `currentUser`), so a UseCase indirection would wrap a one-line call with another one-line call for no benefit at this stage. UseCases become worth adding once a screen needs to *combine* more than one repository's data into one operation — not before.

Dependency injection: **Koin**, not Hilt. Hilt's annotation processing (KSP) adds real build-time and failure-surface cost for a first foundation build with no prior verified-working Android toolchain in this repository; Koin's plain-Kotlin DSL (`module { single { ... } }`, `viewModel { ... }`) gives constructor injection with zero annotation processing, at the cost of losing Hilt's compile-time dependency-graph validation. This is a deliberate first-milestone trade-off, not a permanent one — worth revisiting once the module graph is bigger and compile-time validation's value grows.

Networking: Retrofit + OkHttp + kotlinx.serialization (see section E). WebSocket: `io.socket:socket.io-client` (the official Java/Kotlin Socket.IO client), wrapped in `core:websocket`'s `SocketManager`. Local persistence: Jetpack DataStore (Preferences) for non-sensitive settings, Room deferred until a feature actually needs an offline cache (none does yet — see section J). Secure token storage: `androidx.security.crypto`'s `EncryptedSharedPreferences` (Keystore-backed AES-256). Media/WebRTC layer: not built this milestone — `core:media` stays an empty scaffold folder until Phase 6 (section L).

## B. Module responsibilities

- **`core:common`** — pure Kotlin, no Android dependency. `ApiResult`/`ApiError`: the one result type every repository returns, mirroring the server's `{data}`/`{error}` envelope.
- **`core:network`** — Retrofit/OkHttp setup (`ApiClientFactory`), the `AuthInterceptor` (attaches `Bearer <token>`), the `UnauthorizedNotifier` (a 401 anywhere emits once, app-level nav reacts), `safeApiCall`/`safeAuthCall` (the only way any repository touches Retrofit), and each feature's Retrofit API interface + DTOs (only `auth/` exists so far).
- **`core:websocket`** — `SocketManager`: one Socket.IO connection for the whole app, authenticated via `handshake.auth.token` (see section F). Feature modules subscribe to their own event names on it; nobody opens a second connection.
- **`core:database`** — not yet a real Gradle module (see section J) — reserved for Room entities once a feature needs local caching.
- **`core:datastore`** — `AppPreferences`: ordinary, non-sensitive settings only (currently: last-used login email). The JWT never belongs here — that boundary is deliberate and enforced by the module split, not just a comment.
- **`core:security`** — `TokenStore`/`EncryptedTokenStore`: the one Keystore-backed place the JWT lives.
- **`core:navigation`** — `Routes` (string constants) and `NavigationEvent` (`NavigateTo`/`PopBackStack`), shared between every feature's ViewModels and `:app`'s single real `NavController`. A ViewModel never imports `androidx.navigation` directly.
- **`core:ui`** — the design system: `KothaBartaTheme` (colors pulled from the web app's own `--paper`/`--ink`/`--accent`/`--danger` CSS variables — see section K), typography, spacing scale, and the shared components (`AppPrimaryButton`, `AppTextField`, `FullScreenLoading`/`FullScreenError`/`EmptyState`).
- **`core:media`** — not yet a real module; reserved for the native WebRTC/camera/screen-capture layer (Phase 6, section L).
- **Every `feature/*` module** — owns its own screens (Compose), ViewModels, a repository, and (as of this milestone) its own Koin module exposing that repository and its ViewModels — `:app` never has to know a feature's internal constructors, only that it needs to include that feature's Koin module and route its screens into the shared `NavHost`.

## C. Backend boundary

Restated exactly as `android-games.md` already established, because it does not change with this milestone or any future one: **Android never calculates** a game winner, score, leaderboard reward, turn/move/dice legality, quiz correctness, or challenge result — and, extending the same principle to this milestone's own territory, Android never decides **moderation permission** either (whether an account is muted/banned/restricted is `server/src/utils/moderation.js`'s call alone; a `403 ACCOUNT_MUTED`/`ACCOUNT_RESTRICTED` from the server is rendered as an error message, never pre-empted by a client-side guess). Android only: requests data, sends authenticated actions, receives server-authoritative state, and renders UI. The client-side form checks in `SignupViewModel` (blank fields, password length, confirm-match) are the one apparent exception, and are explicitly *not* an exception to this rule — they exist purely to avoid a wasted round trip for something the form itself can already see is incomplete; the server's own validation (`VALIDATION_ERROR`, `EMAIL_IN_USE`) remains the actual authority, and the client never invents a rule the server doesn't also enforce.

## D. Authentication

**Login**: `POST /auth/login` with `{email, password}`. **Signup**: `POST /auth/register` with `{fullName, email, password, confirmPassword}` — the same fields and the same rules (`password.length >= 8`, `password === confirmPassword`) the server itself enforces (`server/src/routes/auth.js`), checked client-side first only to save a round trip. **Google login**: `POST /auth/google` with `{credential}` — the endpoint already exists server-side (verifies via `verifyGoogleToken`), but wiring the actual Google Sign-In SDK/credential flow on Android is deferred past this milestone (not in the "first coding milestone" scope in section N) — `AuthRepository.loginWithGoogle()` exists and is ready for that wiring whenever it's prioritized.

**The one backend change made in this pass**: `issueSession()` in `server/src/routes/auth.js` now returns the token, and `register`/`login`/`google` include it as a **sibling top-level field** — `{ data: user, token }` — alongside the unchanged `data`. The web client only ever reads `response.data.data` (confirmed by reading `client/src/pages/Auth/hooks/useAuthForm.js`), so this is purely additive and doesn't touch the web app's behavior at all; it's the minimum necessary for a client with no cookie jar to ever obtain a session.

**Token persistence**: `EncryptedTokenStore.saveToken()` immediately after a successful login/register/google response, in `AuthRepository.completeSignIn()` — the same function also connects the Socket.IO client with that token, so "signed in" is one atomic step everywhere it happens, not three things each screen has to remember.

**Logout**: `AuthRepository.logout()` best-effort calls `POST /auth/logout` (harmless even though Android never used the cookie it clears), then always clears the local token and disconnects the socket regardless of whether that call succeeded — a user pressing "log out" must never stay logged in locally just because one network call failed.

**Expired/invalid token handling**: `SplashScreen`/`SplashViewModel` never trusts a stored token on sight — it calls `GET /auth/me` once at startup; a `401` there (expired, revoked, or the account was deleted — see `requireAuth`'s deleted-account check) clears the local session and routes to Login instead of forward into a broken "signed in" state.

**Unauthorized response handling in general**: `UnauthorizedNotifier` (in `core:network`) is fed by an OkHttp interceptor that fires on every `401` from any call, anywhere. `KothaBartaNavHost` collects it once, at the app root, and reacts by clearing the session and navigating to Login — so a token that dies mid-session (not just at startup) is handled the same way, from one place, instead of every future feature's repository needing to special-case a 401 itself.

## E. REST networking

**Retrofit 2.11.0 + OkHttp 4.12.0 + kotlinx.serialization** (via the community `com.jakewharton.retrofit:retrofit2-kotlinx-serialization-converter`, since Retrofit's own official kotlinx.serialization converter ships only from Retrofit 3.x, which — being a very recent major-version release with an API surface not yet well-established in practice — was deliberately not adopted for this first milestone; sticking to the long-stable Retrofit 2.x line lowers risk for a foundation build with no prior verified track record in this repository). Kotlin serialization over Moshi/Gson: no reflection, and it keeps DTOs as plain `@Serializable data class`es with no annotation-processing step.

`ApiEnvelope<T>(data: T?, token: String? = null)` mirrors `{data}`/token-sibling responses; `ApiErrorEnvelope`/`ApiErrorDto` mirror `{error: {code, message}}`. `safeApiCall`/`safeAuthCall` (`core:network`) are the *only* way a repository touches a Retrofit call — they turn a `Response<ApiEnvelope<T>>` into `ApiResult<T>` (or `ApiResult<AuthSession>` for the auth-with-token case), catching `IOException` as `NETWORK_ERROR` and reading the real `{code, message}` off a non-2xx response body rather than inventing a generic message. Backend response contracts were **not** changed except the one additive `token` field justified in section D.

## F. Socket.IO

Android connects with `io(SOCKET_URL, IO.Options().apply { auth = mapOf("token" to jwt) })` — this is exactly the `socket.handshake.auth.token` fallback added to `server/src/server.js` in the prior architecture pass, confirmed still in place and unmodified by this pass. No Android-specific socket events were needed or created — every event name and payload documented in `android-realtime-contract.md` is used as-is.

`core:websocket`'s `SocketManager` is intentionally not wired into any feature UI yet in this milestone (there is no messaging/presence/game feature to consume events from) — `AuthRepository` calls `connect(token)` right after a successful sign-in and `disconnect()` on logout, purely to prove the handshake genuinely authenticates end-to-end before any feature depends on it. Connection lifecycle (reconnect on token refresh, disconnect on app background) beyond that will be designed once the first feature that actually needs a live event (Messages or Presence, per section L) is built.

## G. WebRTC

Not implemented this milestone (`core:media` stays an empty scaffold). Restated from `android-webrtc.md` as the standing plan: Android will need its own native `RTCPeerConnection` implementation (no code shared with `CallProvider.jsx`, which is browser-API-specific), driven by the exact same `call:offer`/`call:answer`/`call:ice-candidate`/`call:signal` messages the server already relays unchanged. Camera/microphone capture, audio routing, screen sharing (`MediaProjection`), permissions, and background/lifecycle survival are all native-only concerns with no web equivalent to port. The signalling/call-state/authorization/database layers are already shared and require no further backend work beyond what section M already flags (TURN).

## H. Games

For each game, the REST/socket/state-model shape is already fixed by the server (see `android-realtime-contract.md` and `android-games.md`); this is the UI-side plan for when each one is actually built (Phase 5/4, section L), not implemented now:

| Game | REST | Socket events | State model | Notes |
|---|---|---|---|---|
| Quiz | `quiz/chapters/:id/sets/:n/start`, `quiz/attempts/:id/answer` | — (REST-only) | `QuizUiState(question, selectedAnswer, isSubmitting, result, error)` | Correctness comes back in the answer response, never computed locally. |
| English/Math games | `game.routes.js` catalog/session endpoints | — (REST-only) | Same shape as Quiz | Questions are server-generated; Android never generates or grades. |
| Tic-Tac-Toe | settings/stats/invites/game-fetch | `ticTacToe:join/move/leave/reaction`, `:state`, `:finished` | `TicTacToeUiState(board, myTurn, connectionState, error)` sourced entirely from the latest `ticTacToe:state` | Reconnect = rejoin the room, discard any local guess, trust the next `:state` push. |
| Ludo | catalog/lobby/invite/settings/ready/start/leave/rematch | `ludo:*` (see contract doc) | `LudoUiState(board, turn, timer, connectionState, takeoverNotice, error)` | `ludo:takeover` must surface as a real UI notice, not be silently dropped — two tabs/devices controlling one seat is a real scenario. |
| Game Challenges | friends/online, active/pending, challenge lifecycle | `gameChallenge:*` | Same question/answer/result shape as Quiz, plus opponent presence | Loading/finished/error states mirror Tic-Tac-Toe's. |
| Leaderboard | `leaderboard/top`, `.../users/:id/stats`, `.../archive/*` | — (REST-only) | Plain paginated list + a "my stats" card | Purely a read surface; no submission path exists or should exist. |

Every row's "loading" state is `FullScreenLoading`, "error" is `FullScreenError` with retry, "empty" is `EmptyState` — all from `core:ui`, not reinvented per feature.

## I. Notifications

Current behavior (unchanged, confirmed still accurate): `Notification` model + `GET /notifications`/`unread-counts` for the durable record, `notification:new` over the existing socket for a live in-app nudge while the app is open — nothing reaches a backgrounded or killed app today. FCM (needed for incoming calls, friend requests, messages, game/Ludo/Tic-Tac-Toe/quiz-challenge invitations, and admin messages while backgrounded) is **not implemented in this milestone** — it isn't required for the Login/Signup/Splash scope in section N, and adding it needs a server-side push-sending piece that doesn't exist yet (`android-readiness.md`'s blockers list this explicitly). It becomes required no later than Phase 6 (incoming calls while backgrounded are the hardest requirement).

## J. Local database

Nothing in this milestone needs Room. The only local persistence is `EncryptedTokenStore` (the JWT) and `AppPreferences` (last-used email) — neither is a cache of server data, both are exactly the kind of small, deliberately-scoped local state that doesn't need a database. Room becomes justified once a feature needs to render *something* before/without a network round trip — the leading candidates, in likely order, are: cached conversation list + recent messages (Messages, Phase 3), then cached profile (Phase 2) and notifications (Phase 2). Sensitive data (the token itself, message plaintext where E2E-encrypted per `android-api-contract.md`'s Messages section) must **not** be blindly cached in a plain Room database — that decision is deferred to whichever feature phase actually adds Room, not decided speculatively here.

## K. UI architecture

`core:ui`'s `KothaColors` object hard-codes the exact hex values from `client/src/App.css`'s `--paper`/`--ink`/`--muted`/`--accent`/`--accent-deep`/`--danger*` CSS variables for both light and dark, so `KothaBartaTheme` produces a Material3 `ColorScheme` that reads as the same brand as the web app — not a generic Material default palette, and not a reskin of the web app's DOM (no WebView anywhere). `Spacing` (4dp-based scale) and `KothaTypography` (system font for now — swappable later without touching any screen, since screens only ever read `MaterialTheme.typography`) round out the foundation. Reusable components built this milestone: `AppPrimaryButton` (owns its own loading-spinner swap), `AppTextField` (label/password/error-text support), and `FullScreenLoading`/`FullScreenError`/`EmptyState`. Dialogs, cards, bottom navigation, and top bars are not built yet — there is no screen in this milestone that needs them; they'll be added by whichever Phase-2+ feature first needs one, following the same "add it to `core:ui` once, reuse everywhere" rule rather than being speculatively pre-built now.

## L. Feature implementation order

Unchanged from the phase plan already agreed in the request, restated here as the living reference for what comes after this milestone: Phase 1 (this milestone) — foundation, auth, networking, token storage, navigation, design system. Phase 2 — Home, Profile, Friends, Notifications. Phase 3 — Messages, realtime messaging, presence (this is where `core:websocket` first gets a real feature consumer and `core:database`/Room likely first becomes justified). Phase 4 — Study, Quiz, Games, Leaderboard. Phase 5 — Tic-Tac-Toe, Game Challenges, Ludo. Phase 6 — Video/audio calls, WebRTC, screen sharing, call notifications (this is where `core:media` first becomes a real module, and where FCM becomes non-optional). Phase 7 — offline/cache, performance, push notifications (if not already pulled forward for Phase 6's call-notification need), polish.

## M. Production blockers

Unchanged from `android-readiness.md`, restated because they remain unresolved and are not addressed by this milestone: (1) `server/.env` is tracked in git with real production secrets (MongoDB credentials, JWT secret, Cloudinary key/secret) — not fixed here, no values reproduced here or anywhere in this pass; (2) those secrets must be rotated manually, as a deliberate decision, before any real production Android rollout; (3) `server/.gitignore` must be updated to exclude `.env`; (4) no TURN server is configured — required before WebRTC call reliability can be trusted in production on cellular networks; (5) no FCM integration exists — required for Android background notifications and incoming-call alerts, no later than Phase 6. None of these were touched, rotated, or worked around in this pass.

## N. First implementation milestone (built in this pass)

Exactly what was scoped, no more: a real Gradle project (`settings.gradle.kts`, root `build.gradle.kts`, a version catalog at `gradle/libs.versions.toml`, and a generated wrapper) with modules `:app`, `:core:{common,network,security,datastore,websocket,navigation,ui}`, and `:feature:auth` — the remaining `core`/`feature` folders stay plain, unregistered directories until the phase that needs them (section L) actually starts. Kotlin 2.0.21 + Jetpack Compose (Compose BOM 2024.12.01) + AGP 8.7.3, chosen as a coherent, well-established version set rather than each dependency's own bleeding-edge "latest" — mixing arbitrary latest-as-of-today versions across a dozen libraries with no prior verified build in this repository was judged too much unnecessary risk for a foundation build whose entire point is proving the toolchain works. Navigation foundation (`core:navigation`'s `Routes`/`NavigationEvent`, `:app`'s single real `NavHost`), network foundation (`core:network`'s Retrofit/OkHttp/interceptors), secure token storage (`core:security`), a basic Socket.IO client (`core:websocket`, connected/disconnected from the auth flow), the common `ApiResult`/`ApiError` models, and the `core:ui` theme/component foundation are all real, working code — not stubs. Three screens: Splash (checks/validates a stored session), Login, and Signup, wired to the real backend via the additive `token`-in-response-body change (section D). No Feed, Messages, Games, Calls, or Ludo code exists anywhere in this milestone; the one screen a signed-in user lands on (`SignedInPlaceholderScreen`) is explicitly labeled as a temporary verification screen with a Logout button, not a Home feature.
