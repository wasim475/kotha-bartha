# Ludo

Real-time multiplayer Ludo inside Kotha-Study (Games → Other → Ludo), plus a fully
offline Local mode. Four modes, one rules engine, a server that is always the
authority.

## The four modes (one registry)

`server/src/games/ludo/variants.js` is the only place a mode is described. The engine,
the server and the UI read it; nothing else branches on a mode id.

| Mode | Online | Players | You win when… | Ranked | Leaderboard |
|---|---|---|---|---|---|
| `QUICK_CAPTURE` – Quick Ludo | yes | 2–4 | you capture an opponent token (match ends at once) | no | yes |
| `CAPTURE_AND_HOME` – Capture + Home | yes | 2–4 | you have captured a token **and** brought one of yours Home | no | yes |
| `CLASSIC_RANKED` – Classic Ranked | yes | 2–4 | all 4 tokens Home; finish order = 1st…4th | yes | yes |
| `LOCAL_CLASSIC` – Local Ludo | no (one device) | exactly 4 | all 4 tokens Home; ranked | yes | no |

A variant declares: id, title, description, category, min/max players, token count,
winning rule, online/local, ranking, leaderboard, reward table and rule
overrides. A new mode is one new entry. Modes can be switched off without touching the
frontend: `LUDO_DISABLED_VARIANTS=CLASSIC_RANKED,...`; the whole game with
`LUDO_ENABLED=false`.

## Architecture

```
server/src/games/ludo/      PURE engine (board, rng, rules, variants, engine) — no React,
                            Socket.IO, MongoDB, HTTP or clock. applyAction(state, action, {now})
server/src/models/          LudoGame (lobby → match → result, private state) · LudoInvite
server/src/services/ludo.service.js   identity, persistence, concurrency, timers, invites, rewards
server/src/routes/ludo.routes.js      REST  (/games/ludo/…)
server/src/sockets/ludo.socket.js     Socket.IO events on the EXISTING server (ludo:*)
client/src/games/ludo/      GENERATED copy of the engine (see below)
client/src/pages/Study/games/ludo/    Home, Lobby, online Game, Local, History, board/dice UI
client/src/components/ludo/           global invitation popup, notification actions
```

**One engine.** The client (ES modules, deployed separately) needs the same rules for
Local mode and for animating the server's results. The server files are canonical; the
client copy is generated by `npm run sync:ludo` (in `server/`), and
`tests/ludo/sync.test.js` fails if the copy is stale. Local Ludo therefore cannot drift
from the online rules.

**Terminology kept separate** (so public matchmaking can be added later without a
rewrite): *Variant* (registry entry) · *Lobby* (`LudoGame.status = "lobby"`, roster +
settings) · *Match* (`status = "active"`, engine state) · *Player* (a seat in the match).
Matchmaking would only need to create lobbies and fill them; nothing else changes.

## The engine

`applyAction(state, action, { now })` → `{ ok, state, events }` or `{ ok:false, error }`.
The input state is never mutated. Actions: `ROLL_DICE`, `SELECT_TOKEN {tokenId}`,
`TIMEOUT`, `LEAVE_GAME`, `DISCONNECT`, `RECONNECT`, `FORFEIT_DISCONNECTED`,
`REQUEST_REMATCH`. Events: `DICE_ROLLED`, `TOKEN_EXITED_HOME`, `TOKEN_MOVED`,
`TOKEN_CAPTURED`, `TOKEN_FINISHED`, `EXTRA_TURN`, `NO_MOVES`, `SIXES_LIMIT`,
`TURN_CHANGED`, `PLAYER_FINISHED`, `GAME_FINISHED`, `DRAW`, `TIMEOUT`, `PLAYER_LEFT`,
`PLAYER_DISCONNECTED`, `PLAYER_RECONNECTED`, `REMATCH_REQUESTED`.

Token position is one integer per token: `-1` base · `0..50` shared track (0 = own start
cell) · `51..55` private home column · `56` Home. The client never sends a position, a
dice value, a seat or a winner — only `ROLL_DICE` or `SELECT_TOKEN {tokenId}` (plus the
`expectedVersion` and an `actionId`).

Dice come from a seeded generator (mulberry32) whose state lives inside the game state.
Online, the seed comes from `crypto.randomBytes`, is stored only on the server and is
stripped from everything sent to clients (`publicState`).

### Configurable rules (`rules.js`, overridden per variant)

`extraTurnOnSix`, `maxConsecutiveSixes` (Nth six in a row forfeits the roll; `0` =
unlimited), `releaseRolls` (dice that bring a token out; default `[6]`), `safeCells`,
`safeCellsProtect`, `exactHome`, `extraTurnOnCapture`, `extraTurnOnHome`,
`autoMoveSingleLegal` (a single legal move is made for you), `turnTimeMs`,
`countdownMs`, `maxTimeoutsBeforeForfeit`, `disconnectGraceMs`, `maxTurns` (draw cap),
`remainingRankBy`. Nothing about them is hard-coded in React.

### Turn time limit (off by default)

**There is no time limit on a turn**: nobody is hurried to roll or move, in any online
mode (`turnTimeMs: 0` in the rules, no timer in the registry, no countdown on screen).
The machinery stays, configurable, for anyone who wants a limit (set `turnTimeMs` in a
variant's `rules`). When a limit is set the server owns the deadline and, when it
passes:

1. the player's timeout counter goes up (any manual action resets it);
2. at `maxTimeoutsBeforeForfeit` (3) the player is treated as away and forfeits (`AFK`);
3. otherwise the server plays the turn: it rolls if the dice weren't rolled, then moves
   **the legal token with the lowest token id**; with no legal move the turn passes.

Being away is still handled: see the reconnect window below.

### Disconnect / reconnect

Leaving the game screen or losing the connection marks the player away (after a short
debounce so a refresh doesn't flash it). The match keeps running on the server's clock
(timeouts still apply). Rejoining restores the full authoritative state; the opponents
see "Reconnecting…" meanwhile. After `disconnectGraceMs` (45 s) without a return the
player **auto-forfeits**; the match is kept, the others are ranked/win by forfeit, and
**no rewards are paid for a forfeit**. Only the tab that joined most recently controls a
player (older tabs get `ludo:takeover` and can take control back).

## Concurrency and idempotency

Every state change is `findOneAndUpdate({ _id, status:"active", stateVersion }, …)`; the
loser of a race re-reads and re-judges (or is told `STALE_VERSION` when it sent an
`expectedVersion`). A replayed `actionId` is acknowledged, not applied again. Results
and rewards are written **in the same atomic update** that moves the match to
`finished`, so a match can be rewarded exactly once.

## Rewards and the leaderboard

Reward tables live in the variant (`points`/`xp` by player count and rank; coins are
architecture only, `0`). A match is rewarded only if it finished by its winning rule or
by a completed ranking, had a minimum number of moves, and had distinct players; players
who forfeited earn nothing. `LudoGame.rankings[].rewardPoints/rewardXp` are the source of
truth: `leaderboardRanking.service.js` sums them into the existing Games leaderboard,
and Ludo stats/history are computed from finished matches only. Level = `floor(sqrt(xp/100)) + 1`.

## Realtime (existing Socket.IO server)

Client → server: `ludo:join`, `ludo:leave`, `ludo:ready`, `ludo:start`, `ludo:roll`,
`ludo:move`, `ludo:chat`, `ludo:reaction`. Server → client: `ludo:invite[:accepted|
declined|cancelled|expired]`, `ludo:rematch[:…]`, `ludo:lobby`, `ludo:lobby:closed`,
`ludo:started`, `ludo:state` (compact public snapshot + the action's events),
`ludo:roll`, `ludo:move`, `ludo:capture`, `ludo:turn`, `ludo:timer`, `ludo:finished`,
`ludo:takeover`, `ludo:chat`, `ludo:reaction`. Rooms: `ludo:{gameId}` (participants only)
and the existing `user:{id}`. Presence for the invite list reuses the existing tracker
(`ticTacToe:presence` events); invitations also appear as `ludo_invite` notifications.

## REST

`GET /games/ludo`, `/variants`, `/history`, `/stats`, `/active`, `/friends/online` ·
`POST /games/ludo/lobbies` · `GET|PATCH /games/ludo/:id` (`/settings`), `POST
/:id/ready|start|leave|rematch|actions` · `POST /games/ludo/invites`, `/:id/accept|
decline|cancel`, `GET /invites/pending`. All are authorised from the session, never from
the body, and re-check the ban/mute policy (`GAME_PLAY`; chat uses `SEND_MESSAGE`).

## Tests

* `npm run test:ludo` (server) — the pure engine (rules, variants, timeouts, reconnect,
  idempotency, random-play invariants) and the engine-copy sync check.
* `npm run test:ludo:integration` (server, needs `MONGODB_URI`; throwaway `ZZ` users only) —
  API + sockets with real users: invites, lobby, play, races, timeouts, sweeper,
  rewards, leaderboard, history, rematch, chat, moderation, feature flags.
* Browser tests drive the real UI with two players (see `tests/ludo-integration/`).

## Known limitations

Friends only (public matchmaking is designed for, not built); no bots (the first version
forfeits abandoned players); music is a small synthesized loop (off by default); sound
and vibration settings are stored per user in the browser.
